# Phase 2 — Permissioned Audit Network Design

Hyperledger Fabric v2.5 permissioned network for the ZeroTrust HRMS audit ledger:
a **multi-organization**, **append-only**, **endorsed** record of authoring
events (employee create/update, role change, document upload/access/revoke).

## 1. Topology

| Component | Identity | MSP | Container |
| --- | --- | --- | --- |
| Orderer (Raft single node) | `orderer.hrms.com` | `OrdererMSP` | `orderer.hrms.com` |
| Org 1 peer | `peer0.hr.hrms.com` | `HROrgMSP` | `peer0.hr.hrms.com` |
| Org 2 peer | `peer0.it.hrms.com` | `ITOrgMSP` | `peer0.it.hrms.com` |
| Org 3 peer | `peer0.finance.hrms.com` | `FinanceOrgMSP` | `peer0.finance.hrms.com` |
| Org 4 peer | `peer0.admin.hrms.com` | `AdminOrgMSP` | `peer0.admin.hrms.com` |

- Peer/orderer images: **2.5.16**; tools container **2.5**; chaincode images
  nodeenv 2.5.15 / ccenv / baseos 2.5.15. Docker Compose project `fabric_hrms`
  on its own docker network so hostnames, TLS SANs and gossip all line up.
- Dev-only PKI generated by `cryptogen` (`crypto-config.yaml`) into
  `fabric/organizations/` — **dev/test keys only, never production**.
- Channel **`hrmsaudit`** created from `configtx.yaml` with a one-per-org
  `Admins` ACL model and default `Application/Writers` policies.
- Chaincode **`hrmsauditcc`** version `1.0` sequence `1`, endorsement policy
  **`OutOf(2, 4 org peers)`** — no single organization can commit an entry alone.

## 2. Trust model (what the network actually gives you)

| Property | Achieved | Notes |
| --- | --- | --- |
| Multi-org endorsement | Yes | 2-of-4; proposals are signed by real org identities |
| Immutable, versioned ledger | Yes | Fabric state + the in-chaincode hash chain |
| Author identity binding | Yes | Each record stores `creatorMsp`, `signerId` (`hf.EnrollmentID`), `txId` |
| No single-org write control | Yes | 2-of-4 policy; single orderer could still reorder but not forge signatures |
| **HA / BFT / no single point of failure** | **No** | 1 orderer, 1 peer per org (dev). See §7. |

The orderer is a **single Raft node**: it can order — but not *sign on behalf of*
organizations — and any forged/unauthorized record would fail the 2-of-4
endorsement policy. The chaincode hash chain additionally detects any tampering
with the *content* of committed records (`verifyChain`).

## 3. Chaincode contract (`chaincode/hrms-audit`)

fabric-contract-api v2.5 contract `HRMSAuditContract` (deployed from source by
external builder):

| Function | Args | Description |
| --- | --- | --- |
| `submitAudit(eventType, actorId, subjectId, payloadJSON)` | `[string,string,string,string]` | Append a record with the caller's MSP/signer id and peer timestamp. Enforces org membership by construction (endorsement) and internal guards. |
| `querySeq()` | `[]` | Current sequence (append counter, `seq` state key). |
| `queryAll(startSeq, endSeq)` | `[int?,int?]` | Range read of records (defaults `1..seq`). |
| `queryBySubject(subjectId)` | `[string]` | Records for one subject (rg key range). |
| `queryByType(eventType)` | `[string]` | Records of one event type. |
| `verifyChain()` | `[]` | Recompute the hash chain over the stored ledger; returns `{seq, intact, issues[]}`. |

Record schema (metadata only — no document plaintext, no keys):

```json
{ "seq": 3, "eventType": "ACCESS_REVOKED", "actorId": "user-4f2a1c",
  "subjectId": "doc-9f8e3c", "payload": { "reason": "separation" },
  "creatorMsp": "AdminOrgMSP", "signerId": "unknown",
  "ts": "2026-09-18T19:29:00.562Z",
  "txId": "e8213c...4229c",
  "prevHash": "0185779a...e9328e", "hash": "0d9902f1...80b27" }
```

Hash scheme (self-consistent): `record.hash = sha256(canonical(record with
`hash` omitted))`; the *next* record's `prevHash = sha256(canonical(full stored
previous record including its hash))`. Genesis `prevHash` is
`0000...0000`. `verifyChain` recomputes every link and reports any mismatch.

## 4. Identity model

- Each org: CA certificate, admin identity (`Admin@<org>.hrms.com`), peer
  identity. TLS is **always on** (`--tls true`, `tlsca` root certs).
- Proposals must satisfy the channel's `Application/Application.Writers`
  policy — identities from non-member MSPs (e.g. `OrdererMSP` orders through
  the app channel) are rejected at the peer **before** endorsement
  (`Failed evaluating policy on signed data ... 0 sub-policies were satisfied`).
- `cryptogen` certs carry **no enrollment-id** field, so `signerId` falls back
  to `"unknown"`; the identifying fields that ARE present for dev identities are
  `creatorMsp` + `txId` + keystore subject. With Fabric CA identities
  `hf.EnrollmentID` would populate `signerId` for real.

## 5. Chaincode lifecycle (Fabric v2.x governance)

Run by `fabric/scripts/deploy-chaincode.sh` (idempotent):

1. package `hrmsauditcc` (source, external builder)
2. install on **all 4** peers
3. `approveformyorg` — **one approval per org, no orderer call**
   (`approveformyorg` is a channelless call: cross-org `--peerAddresses` there
   is forbidden by the `Admins` ACL, so approvals are single-org loops)
4. `commit` with all 4 `--peerAddresses`
5. verify committed sequence + approvals

Practical governance facts learned the hard way:

- The lifecycle endorsement policy is `MAJORITY Endorsement`; on a **fresh**
  channel a single organization can get its approval committed at sequence 1.
- Re-approving the **same sequence** with a *different package digest* yields
  `ENDORSEMENT_POLICY_FAILURE` (the lifecycle chaincode sees the decision as
  already made). Upgrades therefore **bump the sequence** (`querycommitted` +
  `SEQUENCE=current+1`), which is exactly what `deploy-chaincode.sh` does.

## 6. Backend integration (this repo)

`src/ledger/fabric.ts` — `FabricLedger` implements `LedgerBridge`:

- gRPC to the endorsed peer (`localhost:7051` from Windows into the WSL2 dev
  network; TLS with the org `tlsca`; `checkServerIdentity` validates the peer's
  SAN `peer0.hr.hrms.com` because the TCP endpoint differs from the cert name).
- Signing identity: `HROrgMSP` admin key/cert from the MSP config dir.
- Submit: `contract.submit('submitAudit', { arguments, endorsingOrganizations:
  [HROrgMSP, FinanceOrgMSP] })` → waits for **commit**, returns `{committed,
  seq, eventType, ...}`.
- Query: `querySeq` + `verifyChain` + `queryAll` mapped into a typed snapshot.
- `LEDGER_BACKEND=fabric` gates everything; default `off` preserves Phase 1
  behavior exactly (local SQLite blockchain mirror, honestly labeled).

## 7. Honest limitations (say these out loud)

- **One orderer (Raft single node)** → ordering is a SPOF and not Byzantine.
- **One peer per org** → an org cannot independently disagree itself.
- **cryptogen dev keys** in the repo tree → not production PKI.
- **No CouchDB/private data collections**; payload is a bounded JSON blob in
  the ledger (≤4KB).
- Network-level IDs are `creatorMsp`/`signerId`/`txId`; the API layer decides
  which events reach the ledger and with what business meaning.
- Fabric is *permissioned*: decentralization here means "no one organization
  controls the audit history alone", not "anyone can read/write".
